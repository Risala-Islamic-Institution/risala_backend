Quick Start
Get up and running with ShegerPay in minutes.

1. Install the SDK

npm install @shegerpay/sdk

2. Verify a payment

import ShegerPay from '@shegerpay/sdk';

const client = new ShegerPay('sk_test_YOUR_API_KEY');

const result = await client.verify({
  provider: 'telebirr',
  transactionId: 'DHQ56AE0I7',
  amount: 500,
});

console.log(result.verified); // true

// CBE is verified from the receipt image — see "Verify a CBE payment" below.

Or use cURL directly

curl -X POST https://api.shegerpay.com/api/v1/verify \
  -H "X-API-Key: sk_test_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"provider":"telebirr","transaction_id":"DHQ56AE0I7","amount":500}'

Authentication
All API requests require authentication. ShegerPay supports two methods:

X-API-Key (Server-to-Server)

Use for backend integrations, SDKs, and server-side calls.

X-API-Key: sk_live_YOUR_API_KEY

Works with all endpoints. Recommended for production.

Authorization: Bearer (Firebase or Compatibility)

Use Firebase ID tokens for dashboard/frontend. Bearer API keys are also accepted for backward compatibility.

Authorization: Bearer FIREBASE_ID_TOKEN
# or: Authorization: Bearer sk_live_YOUR_API_KEY

For new server integrations, use X-API-Key.

Which should I use?

• Building a backend integration? → Use X-API-Key

• Building a frontend app? → Use Authorization: Bearer with Firebase

• Both headers work on all authenticated endpoints. If both are provided, X-API-Key takes priority.

Test Keys

Prefix: sk_test_, safe for development, no real transactions

Live Keys

Prefix: sk_live_: runs live verification and provider operations, keep secret

Demo Sandbox Key

Try the API instantly without creating an account:

X-API-Key: sk_test_demo

This built-in key works on all endpoints in test mode. Verification always succeeds (unless transaction ID contains "FAIL"). No real money is processed.

Custody Model

ShegerPay does not hold customer funds. Ethiopian verification endpoints (/verify, /verify-image, /quick-verify) are non-custodial and settle on bank/provider rails. Card rails may include temporary authorization holds by issuing/acquiring processors; those holds are external to ShegerPay custody.

Standard Verification Response

{
  "verified": true,
  "valid": true,
  "status": "verified",
  "mode": "test",
  "request_id": "req_abc123",
  "reference_id": "SHGR-...",
  "saved": true
}

verified and valid are both returned for compatibility. New integrations should read verified.

Common Error Codes

400 missing/invalid request fields or receipt image has no transaction.

401 missing, invalid, revoked, or wrong API key.

402 plan or monthly quota does not allow this action.

429 rate limit reached. Retry after the response window.

503 provider/OCR service is temporarily unavailable.

Example: verify CBE payment (receipt image)

curl -X POST https://api.shegerpay.com/api/v1/verify-image \
  -H "X-API-Key: sk_test_YOUR_KEY" \
  -F "provider=cbe" \
  -F "amount=500" \
  -F "merchant_name=My Shop" \
  -F "screenshot=@cbe-receipt.jpg"

CBE is verified from the receipt: the QR on it resolves against CBE's receipt service, and a typed FT… transaction ID is accepted again since 2026-09-13 (CBE looks it up with the last 8 digits of the receiving account, taken from the merchant's linked CBE account). If you already have the receipt link you can send it as the transaction_id to /verify instead:{"provider":"cbe","transaction_id":"https://mbreciept.cbe.com.et/v2-…"}. Other providers are unchanged. `/verify` accepts both JSON and form-encoded payloads.

  -H "Content-Type: application/json" \

Example: verify BOA payment

curl -X POST https://api.shegerpay.com/api/v1/verify \

⚠ eBirr & Awash require the FULL Receipt URL

As of 2026 the eBirr and Awash receipt portals use opaque-token URLs. The numeric Ref/Txn ID alone no longer resolves to a receipt. Your integration must send transaction_idas the entire Receipt Link from the buyer's SMS.

Error codes returned for bad input:

EBIRR_NUMERIC_ID_ONLY — buyer sent the numeric Ref/Id instead of the full link
EBIRR_LEGACY_URL_DEAD — old transactioninfo.ebirr.com URL (host retired)
EBIRR_INVALID_FORMAT — unrecognised input
AWASH_NUMERIC_TXNID_ONLY — buyer sent the numeric Txn ID instead of the Receipt Link
AWASH_INVALID_FORMAT — unrecognised input
All cases return HTTP 200 with {"valid":false, "status":"invalid_input", "error_code":"…", "reason":"…"}. Branch on error_code (not the prose) to handle this in your code.

Example: verify eBirr Kaafi payment

curl -X POST https://api.shegerpay.com/api/v1/verify \
  -H "X-API-Key: sk_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"provider":"ebirr_kaafi","transaction_id":"https://receipt.ebirr.com/kaafimf/CI7t6ONdWKp-EWHQjog2Bw","amount":100,"merchant_name":"My Shop"}'

Optional: reject if the sender name doesn't match

Add expected_sender_name to any verification call to confirm who paid, not just that the payment happened. Works on /verify, /verify-image and /quick-verify. First name alone is enough — "Abebe" matches "Abebe Kebede". Case, word order and small typos are tolerated.

curl -X POST https://api.shegerpay.com/api/v1/verify \
  -H "X-API-Key: sk_live_YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"provider":"cbe","transaction_id":"FT26062K7WMY","amount":500,"expected_sender_name":"Abebe Kebede"}'

On a mismatch the payment is rejected and the transaction is not consumed — it can still be verified again with the correct name:

{
  "valid": false,
  "status": "failed",
  "provider_status": "sender_name_mismatch",
  "sender_name_match": false,
  "reason": "Rejected: sender name mismatch. The receipt sender does not match expected_sender_name."
}

Match → "valid": true with "sender_name_match": true.
Receipt has no readable sender name → still verifies, with "sender_name_match": null. A real payment is never rejected over a missing bank field.
Omit the field → behaviour is exactly as before. The check only runs when you send it.

Retry Behavior
Failed webhook deliveries are retried with exponential backoff:

1st

Immediate

2nd

10 sec

3rd

30 sec

4th

1 min

5th

2 min

After 5 failed attempts, the webhook is queued for later retry. A 2xx response is considered successful.

Signature Verification
Every webhook includes an HMAC-SHA256 signature in the X-ShegerPay-Signature header. Verify it to ensure the payload is authentic.

Headers sent with every webhook:

X-ShegerPay-Event: payment.verified
X-ShegerPay-Delivery-ID: abc123def456
X-ShegerPay-Signature: sha256=<hmac_hex_digest>
Content-Type: application/json
User-Agent: ShegerPay-Webhook/2.0

Verify in Python

import hmac, hashlib

def verify_webhook(payload_body: str, signature_header: str, secret: str) -> bool:
    expected = hmac.new(secret.encode(), payload_body.encode(), hashlib.sha256).hexdigest()
    provided = signature_header.replace("sha256=", "")
    return hmac.compare_digest(expected, provided)

Verify in Node.js

const crypto = require('crypto');

function verifyWebhook(body, signatureHeader, secret) {
  const expected = crypto.createHmac('sha256', secret).update(body).digest('hex');
  const provided = signatureHeader.replace('sha256=', '');
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(provided));
}

Rate Limits
API requests are rate-limited per user (authenticated) or per IP (unauthenticated).

Endpoint	Limit	Window
/verify, /quick-verify	100 req	60 sec
/payment-links	50 req	60 sec
/webhooks	30 req	60 sec
/api-keys	20 req	60 sec
/auth, /two-factor	5-10 req	60 sec
All other endpoints	200 req	60 sec
Rate limit headers are included in every response: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Window. After 10 consecutive violations, your IP/user is locked out for 5 minutes.

FAQ
Common questions from developers integrating ShegerPay.

When should I use X-API-Key vs Authorization: Bearer?

Use X-API-Key for server-to-server integrations (your backend calling our API). Use Authorization: Bearer with a Firebase ID token for frontend/dashboard calls. Authorization with sk_/pk_ API keys is also accepted for compatibility, but X-API-Key is preferred for new integrations. If both are provided, X-API-Key takes priority.

Does ShegerPay hold customer funds?

ShegerPay does not hold customer funds. Ethiopian bank/mobile and crypto verification flows settle directly on provider rails. Card payments can have temporary authorization holds by issuing/acquiring processors, but that is processor behavior, not ShegerPay custody.

What happened to POST /international/gmail/setup?

That old setup endpoint is not part of the public API. Non-PayPal international verification is private/assisted right now, so public docs focus on PayPal, Ethiopian verification, crypto, payment links, and webhooks.

Which international providers are supported?

PayPal is the public international product for checkout, balance, and payout workflows. Other international rails are verification-only/private setup right now and are intentionally hidden from public API docs.

Does a webhook fire when a payment is auto-verified via email?

For private/assisted international verification setups, webhook events can be enabled by support. Public docs currently focus on PayPal, Ethiopian verification, crypto, payment links, and standard webhooks.

Do you retry failed webhook deliveries?

Yes. We retry up to 5 times with exponential backoff: immediate → 10s → 30s → 1min → 2min. After all retries fail, the webhook is queued for later retry. A 2xx response is considered successful.

How can I test webhooks?

Use POST /webhooks/test with your webhook_id and optional event_type parameter to send a sample event for any supported type. In the dashboard, each webhook has a dropdown to select the event type before clicking Test. You can also use test API keys (sk_test_) which process test transactions that trigger real webhook deliveries.

Is there a sandbox for international payments?

Use test API keys (sk_test_) for public PayPal and verification flows. Non-PayPal international setup is private/assisted right now and does not create wallet balance or payout funds.

How fast is auto-verification after email forwarding?

Email-forwarding auto-verification is available only for private/assisted international setups right now. Public integrations should use PayPal checkout/payouts, Ethiopian verification, crypto verification, and payment links.

Can I export my transactions?

Yes. Use GET /transactions/export to download a CSV file with all your transactions (up to 1,000). Includes date, transaction ID, provider, amount, currency, status, customer, and description columns.

How do I see webhook delivery history?

Use GET /webhooks/{id}/deliveries to fetch the last 10-50 delivery attempts for any webhook. Each log entry includes the event type, HTTP status code, retry count, and timestamp. You can also view delivery logs in the Dashboard under Webhooks, Logs.

Can I link Ethiopian banks via API?

Ethiopian bank verification (CBE, Telebirr, etc.) works via the /verify endpoint, no account linking needed — pass the provider and transaction_id. CBE is the exception: it is verified from the receipt itself, so upload the receipt image to /verify-image (or pass the mbreciept.cbe.com.et receipt link as the transaction_id).

How do I set a default international account?

Default international account management is hidden from public docs while non-PayPal international rails remain private/assisted. Use the PayPal section for public international checkout and payout workflows.

Are there rate limits?

Yes. Verification endpoints allow 100 req/min, payment links 50 req/min, and most other endpoints 200 req/min. Check X-RateLimit-Remaining headers in responses. See the Rate Limits section above.
